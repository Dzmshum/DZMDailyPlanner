# Smart Commit

Проанализируй все незакоммиченные изменения, сгруппируй их по смыслу, составь план коммитов, получи подтверждение пользователя и только затем создай локальные коммиты.

## 🔒 Безопасность

Скилл **никогда** не изменяет содержимое файлов и не выполняет операции с удалённым репозиторием.

**Запрещено:**

- `git push`, `git pull`, `git fetch`;
- `git reset --hard`, `git clean`, `git checkout -- <files>`;
- `git restore <files>` без `--staged`;
- `git rebase`, `git merge`, `git cherry-pick`;
- `git commit --no-verify`;
- отключение или обход git hooks;
- автоматическое редактирование, форматирование или исправление файлов;
- пустые commits и `git commit --allow-empty`.

**Изменять состояние репозитория разрешено только:**

- `git add <files>`;
- `git restore --staged <files>`;
- `git commit -m "..."` — только subject, без body.

`git add -p` не использовать: интерактивный режим ненадёжен для agent environment.

Read-only команды (`git status`, `git diff`, `git log`, `git branch`, `git show`, `git rev-parse` и т.п.) разрешены для анализа.

### Обязательная остановка

До начала изменений проверь:

- нет merge/rebase/cherry-pick;
- нет конфликтов;
- `HEAD` не detached;
- текущая branch не защищённая: `main`, `master`, `dev`, `develop`, `release/*`, `hotfix/*`;
- нет потенциальных секретов.

Если staging не пуст — покажи, что уже в staging, и предложи снять через `git restore --staged`. Остановись только если пользователь отказался или ситуация неоднозначна.

Если любое другое условие нарушено — не изменяй репозиторий, объясни причину и остановись.

Потенциальные секреты включают, например:

`.env`, `credentials`, `secrets.*`, `private-key.*`, `*.pem`, `*.key`.

Также проверь изменённые строки на распространённые секреты: private key blocks (`BEGIN ... PRIVATE KEY`), API tokens, access tokens и другие явно похожие credential values.

При подозрении на секрет остановись. Не пытайся его удалить, замаскировать или исправить.

Шаблоны вроде `.env.example` сами по себе секретом не считаются.

Если staging после `git add` не соответствует плану — сними staging только через `git restore --staged` и остановись.

Если проверка или `commit` завершились ошибкой — не исправляй код, не объединяй и не переставляй группы и не обходи hooks.

## 1. Анализ изменений

1. Проверь branch, `HEAD`, staging и состояние незавершённых git-операций.
2. Получи изменения через `git status --porcelain`.
3. Учти `modified`, `added`, `deleted`, `renamed`, `untracked`.
4. Игнорируй только явный шум:
   - `*.log`
   - `*.tmp`
   - `*.swp`
   - `.DS_Store`

   Не удаляй его и не добавляй в commits.
5. Сначала оцени объём через `git diff --stat`, затем изучи diff текстовых файлов.
6. Для `untracked` прочитай содержимое.
7. Binary-файлы не анализируй как текст — учитывай имя, размер и контекст использования.

Если после исключения шума не осталось изменений для коммита — остановись и сообщи об этом.

## 2. Группировка

Группируй изменения по приоритету:

1. смысловая связь;
2. общая задача или feature;
3. зависимости между изменениями;
4. директория или module — только как слабый сигнал.

Тесты, конфиги, dependencies и документацию включай в группу той функциональности, которую они обслуживают.

Не создавай отдельный commit только из-за типа файла.

Каждая группа должна представлять логически завершённое изменение и содержать хотя бы одно реальное изменение в diff.

### Изменения внутри одного файла

Если один файл содержит несколько независимых логических изменений, но их нельзя безопасно разделить без интерактивного `git add -p`, **не останавливайся**.

Включи весь файл в одну группу и объедини соответствующие логические изменения в один commit.

Например:

```
src/foo.ts:
  изменение A → commit 1
  изменение B → commit 2

если файл нельзя безопасно разделить, планируй:
  commit 1+2
```

Не объединяй при этом другие независимые файлы или задачи только ради удобства staging.

Порядок commits определяй по зависимостям. Если зависимости нет — сначала группы с меньшим риском.

## 3. Проверки проекта

В первую очередь ориентируйся на стек проекта.

### Node.js / package manager

Проверь `package.json`, lock-файл и поле `packageManager`.

Определи package manager по `packageManager` или lock-файлу (`yarn.lock`, `package-lock.json`, `pnpm-lock.yaml`) и используй соответствующие команды.

Если `packageManager` и lock-файлы конфликтуют или найдено несколько несовместимых lock-файлов — не выбирай package manager автоматически. Остановись, опиши конфликт в плане и дождись уточнения пользователя.

Определи реально доступные scripts: `test`, `lint`, `typecheck`, `build`.

Не придумывай команды, которых нет в проекте.

Для других стеков используй только явно настроенные команды из конфигурации проекта.

Если автоматические проверки надёжно определить нельзя — сообщи об этом в плане и не выдавай отсутствие проверок за успешную проверку.

### Проверки каждой группы

Для каждой группы:

- запускай релевантные тесты, если их можно надёжно определить;
- запускай `lint` и `typecheck`, если они настроены;
- не запускай полный test suite перед каждым commit без необходимости.

Если релевантные тесты определить нельзя:

- запусти полный test suite, если это предусмотрено проектом и разумно для текущего изменения;
- иначе явно укажи, что релевантные тесты не определены.

### Изменения повышенного риска

Если группа изменяет:

- dependencies;
- `package.json`;
- lock-файл;
- конфигурацию build;
- конфигурацию тестов;

перед commit запусти полный test suite и `build`, если они доступны.

### Важное ограничение тестов

Проверки выполняются в текущем working tree.

Пока другие группы ещё не закоммичены, их незастейдженные изменения могут влиять на результат тестов.

Поэтому не утверждай, что тесты доказывают независимую работоспособность конкретного будущего commit.

### Побочные изменения

Перед проверками запомни `git status --short`, после каждой проверки сравни его с исходным состоянием.

Не добавляй автоматически файлы, созданные:

- tests;
- lint;
- build;
- git hooks.

Особенно внимательно относись к generated files, snapshots и `dist`.

Если происхождение нового изменения неоднозначно — остановись.

Hooks разрешены и не обходятся. Если hook создал или изменил файлы либо staging во время commit, не исправляй и не откатывай результат — остановись и сообщи пользователю.

## 4. План

До первого изменения репозитория обязательно покажи план.

План должен содержать:

- группы и входящие файлы;
- объединённые commits, если один файл нельзя безопасно разделить;
- порядок commits;
- сообщение каждого commit;
- проверки каждой группы;
- финальные проверки.

После этого запроси подтверждение пользователя.

Если пользователь отказался — заверши работу без изменений.

## 5. Создание commits

После подтверждения для каждой группы:

1. Добавь только запланированные файлы в staging.
2. Проверь `git diff --cached`.
3. Убедись, что staged diff не пуст и соответствует плану. Если diff пуст — не создавай commit, остановись и сообщи причину.
4. Запусти запланированные проверки.
5. Если проверки прошли — выполни `git commit -m "..."`.
6. Если проверки упали — **не создавай commit**, остановись и сообщи результат.
7. Не используй `--no-verify`.
8. После commit выполни `git status --short`.

Если hook создал или изменил файлы — не добавляй их автоматически в следующие commits.

Если staging или состояние working tree стало неожиданным — остановись и сообщи причину.

## 6. Повторный запуск после остановки

Если скилл остановился после создания части commits, не откатывай уже созданные commits.

При повторном запуске:

- анализируй текущее состояние репозитория заново;
- работай только с оставшимися незакоммиченными изменениями;
- не пытайся повторно создать уже существующие commits.

## 7. Финальная проверка

После успешного создания всех запланированных commits:

1. Покажи hash и сообщение каждого созданного commit.
2. Запусти полный `test`, если он доступен.
3. Запусти `build`, если он доступен и предусмотрен проектом.
4. Покажи итоговый `git status --short`.
5. Перечисли оставшиеся изменения и проигнорированный шум.
6. Напомни, что `git push` пользователь выполняет самостоятельно.

Если финальные проверки упали — не откатывай commits, только сообщи результат.

## 📝 Сообщения commits

Формат — только subject, без body:

```
<тип>(<компонент>): <краткое описание>
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

Правила:

- описание — на русском, в прошедшем времени: что уже сделано в этом commit;
- технические термины и названия сущностей оставляй на английском;
- глагол в прошедшем времени — «добавил», «исправил», «обновил»; не «добавить», «исправить», «обновить»;
- без точки в конце;
- компонент — затронутая область или module;
- если в имени branch есть однозначный issue ID, добавь его вместо компонента.

Примеры:

```
feat(auth): добавил refresh token для API
fix(api): исправил обработку timeout
refactor(BIGDATA-1111): упростил обработку состояния формы
test(auth): добавил тесты для login flow
chore(cursor): добавил skills smart-commit и smart-optimization
```

## ⚙️ Режимы

- `--dry-run` — только анализ и план, без изменений в репозитории.
- `--no-tests` — пропусти только тесты; остальные проверки и правила безопасности сохраняются. В финальном отчёте явно укажи, что тесты были пропущены пользователем.
