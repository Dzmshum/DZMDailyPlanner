# Smart Optimization

Проверь изменённый код на ошибки и возможности обоснованной оптимизации.

Цель — сделать код корректнее, проще, надёжнее и эффективнее, **не усложняя его без необходимости и не меняя рабочую архитектуру ради самого refactor**.

## Scope

Работай только в границах текущей задачи:

- файлы из `git diff`, staging или явно указанные в чате;
- связанные модули и публичные контракты, которые затронуты этими изменениями.

Не делай drive-by cleanup соседних файлов. Не трогай чужой diff и код вне scope задачи. Untracked-файлы в scope текущей задачи — включай; посторонние untracked — не трогай.

## 1. Анализ

Изучи контекст файлов в scope и проверь:

### Correctness

- bugs, edge cases, `null` / `undefined`, типы;
- `async` / `await`, Promise, обработка ошибок, race conditions;
- memory/resource leaks, unreachable или лишний код;
- security-риски в затронутом коде.

### Performance

Ищи только обоснованные проблемы: лишние вычисления, повторные операции, лишние `render` / `update`, повторные network/API requests, N+1, неэффективная работа с большими коллекциями.

Не делай premature optimization без понятной причины.

Не заменяй простые операции на более сложные структуры данных без подтверждённого или очевидного выигрыша для реального объёма данных проекта. Например, не превращай каждый `.find()` в `Map` или `Set` только ради теоретической сложности O(n).

### Maintainability

- чрезмерная сложность, дублирование, слишком большие functions;
- неочевидные зависимости, плохие имена;
- нарушение patterns проекта, устаревший или недостижимый код.

Не переписывай рабочий код только ради другого style.

### Documentation

Проверяй документацию **только если** изменённый код влияет на описываемое публичное поведение, конфигурацию, setup или пример использования.

Локальный внутренний refactor без смены контракта — не повод искать правки в README и прочих docs.

Если проверка уместна — смотри JSDoc/TSDoc и комментарии к изменённым public API, props, hooks, utils; setup/config-подсказки, API-описания и примеры, **которые напрямую описывают затронутое поведение**. README трогай только если изменение затрагивает описанный в нём setup, конфигурацию или публичное использование проекта.

Ищи расхождения с кодом: сигнатуры, шаги запуска, default values, side effects, error cases.

Не трогай `.cursor/`, CHANGELOG, ADR и project skills/rules, если задача явно не про них.

## 2. Приоритет

Оцени найденные проблемы:

1. **Critical** — серьёзный bug, crash, потеря данных или security issue.
2. **High** — вероятный bug или существенная проблема performance.
3. **Medium** — заметное улучшение correctness или maintainability.
4. **Low** — косметический или спорный refactor.

В первую очередь исправляй Critical и High.

Medium исправляй только если изменение небольшое и польза очевидна — **не больше 1–3 таких правок за прогон**. Остальные Medium/Low — в итог как предложения, без автопатча.

## 3. Принципы оптимизации

- Не усложняй код ради теоретической оптимизации.
- Не добавляй dependencies без необходимости.
- Не меняй публичные API без причины.
- Сохраняй существующую архитектуру и patterns проекта.
- Не меняй поведение, не связанное с текущей проблемой.
- Предпочитай простое решение сложному.
- Не делай массовый refactor, если достаточно локального исправления.
- Если текущий код уже достаточно хорош — ничего не меняй.

## 4. Исправление

Перед внесением изменений, если возможно, зафиксируй исходные diagnostics и результаты checks по файлам в scope — чтобы отличать pre-existing errors от ошибок, появившихся после оптимизации.

Если найдены очевидные ошибки или обоснованные улучшения — внеси необходимые изменения самостоятельно.

Если изменение существенно меняет архитектуру, API или поведение либо его польза неоднозначна — сначала объясни проблему и предложи вариант, не внося такое изменение автоматически.

### Tests

Если изменилось поведение — обнови существующие tests под новую логику в уже существующих test-файлах.

Новый test-файл можно добавить **только если одновременно**:

- изменённая логика не покрывается существующими test-файлами;
- тест нужен для проверки исправленного **Critical** или **High** bug.

Во всех остальных случаях новые test-файлы не создавай — опиши пробел в покрытии в итоговом отчёте.

### Актуализация документации

Обновляй существующую документацию только при прямом влиянии изменений на публичное поведение, конфигурацию, setup или пример использования. Внутренние правки без смены контракта — docs не трогай.

Новые `.md` и прочие doc-файлы **только по явному запросу пользователя**. Не делай массовый rewrite docs без явной пользы.

Если документация требует существенной переработки — опиши, что устарело, не меняя docs автоматически.

## 5. Проверка результата

После изменений проверь итоговый код и доступные project checks.

Сначала посмотри diagnostics/linter errors для изменённых файлов, если инструмент доступен.

Определи package manager по `packageManager` или lock-файлу и используй только реально существующие scripts из `package.json`.

Если `packageManager` и lock-файлы конфликтуют или найдено несколько несовместимых lock-файлов — не выбирай package manager автоматически. Сообщи о конфликте и не запускай package manager-специфичные checks, пока пользователь не уточнит.

Минимальный набор: релевантные tests, `lint` и `typecheck` — если доступны. `build` — только если менялись типы, экспорты, сборка или bundling.

### Частично упавшие checks

Если check падает из-за ошибки вне scope или из-за уже существующей проблемы — **не исправляй её автоматически**.

Сравни результат с исходным baseline и явно раздели в отчёте:

- **новые** ошибки — в файлах scope, появившиеся после твоих изменений;
- **pre-existing** — были до оптимизации или в файлах вне scope.

Не сообщай просто «lint failed» / «typecheck failed» без этой разбивки.

Исправляй только ошибки, появившиеся непосредственно в результате твоих изменений. Pre-existing и ошибки вне scope — не трогай; перечисли в итоге отдельно.

Если baseline зафиксировать не удалось, но ошибка явно не в изменённых файлах scope — считай её pre-existing и не патчи автоматически.

Полный test suite запускай, если:

- изменена shared logic;
- затронуто несколько связанных модулей;
- изменение может повлиять на другие части приложения;
- релевантные tests невозможно надёжно определить.

Если проверки недоступны — сообщи об этом.

Не утверждай, что код протестирован, если соответствующие tests фактически не запускались.

## 6. Итог

После проверки кратко сообщи:

- что было найдено (с приоритетами);
- что исправлено;
- какие оптимизации сделаны;
- что обновлено в документации и tests (или что оставлено без изменений и почему);
- какие checks запущены и их результат — отдельно **новые** и **pre-existing** ошибки;
- что сознательно не изменялось и почему;
- предложения по Medium/Low, которые не вносились.

Если существенных проблем нет — прямо скажи, что код уже выглядит корректно и дополнительных изменений не требуется.

Для коммита изменений используй `@smart-commit`; сам коммиты не создавай.
